# Backend repair validation

Migration: `supabase/migrations/20261006173732_premium_backend_security.sql` is the live-project repair, based on audited live schema. The nested historical Flutter SQL files describe an older incomplete baseline; this migration must follow the live catalog/game migrations, rather than being applied alone to an empty database.

Behavior suite: wrap the migration (for pre-deployment validation) and `supabase/tests/premium_backend_behavior.sql` in `BEGIN; ... ROLLBACK;` via SQL tooling. After deployment, run only the behavior suite inside BEGIN/ROLLBACK. The suite uses UUIDs in the `00000000-0000-4000-8000-0000000001xx` range and fixture room/gift/moment rows. It never spends real users' coins. Auth-user fixtures consume sequence values even on rollback; no IDs are renumbered.

The initial VIP grant regression failed on the live database before the repair. The full migration and suite passed in a rollback transaction on 2026-10-06. A subsequent read confirmed zero fixture users and no `room_moderators` table, proving no schema/data deployment remained. Tested authorization, safe profile edits, password secrecy, safe ranking reads, restricted room creation, tag forgery, seat exclusivity, moderator exit/chat cleanup, wallet privacy, gift tier expiry, gift 45%/5% split and retry, evidence-based counters, room-only/disabled games, pgcrypto wheel execution and game retries.

`play_game` retains the five existing parameter names and adds `p_room uuid default null`. Omitted room resolves the caller's current sole room; it never permits lobby gaming. Result JSON is unchanged. `profile_gifts(p_user)` returns `gift_id,name,image_path,quantity`; image_path aliases gift asset_path. The `voice_access(p_room,p_user)` authorization helper is executable only by service_role.

The ranking view uses security_invoker and explicit public columns. Direct room reads must name safe columns, because `SELECT *` would include the protected password hash and fails. `my_rooms` removes password_hash from nested JSON. Rooms, profiles, existing wallet balances and historical reward records remain intact. Lifetime totals start from retained events/ledger; deleted historical likes/comments cannot be reconstructed. Wealth/charm counters reflect historical evidence. Active points remain zero until an authoritative activity policy is defined; no level thresholds or user status are invented.

Voice tokens retain loginToken/channelToken/server/accountUri/channelUri/expiresAt and add canTransmit. Issuance requires a valid authenticated active profile, UUID room, open room, current membership and no room ban, including private rooms. Listeners can join with canTransmit=false. Vivox join tokens do not themselves enforce seat/mute status or evict an already-connected user after a ban. Provider channel moderation/forced removal requires deployed Vivox moderation integration and device testing; the app must begin muted and follow seat changes. Source is synchronized in both Supabase function directories.

Uniqueness indexes intentionally fail on legacy duplicate open owner rooms, current memberships or occupied seats instead of deleting records. Read-only preflight found zero duplicates. Moderator assignments persist separately when leaving; presence is always removed. No balance reset, account deletion, manual 5M provenance adjustment or committed live deployment is included here.
